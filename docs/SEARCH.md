# 検索

困っていること：検索がタイトル・要約（本文の先頭 400 文字）・フィード名しか見ないので、本文の中ほどにある言葉では見つからない。「この語を含まないもの」「どちらか」も書けない。

ほかのリーダーでは Inoreader の全文検索と検索の書き方にあたる（[research/feed-readers.md](research/feed-readers.md)）。

## 決定

- **探すところ**：タイトル・要約・**本文**（全文取得した本文があればそちら）・フィード名。本文は HTML を除いた文字で探す
- **書き方**（⌘F の検索欄）
  - 空白で区切ると、すべてを含むもの（今までどおり）。全角の空白でもよい
  - `"語句"`：空白を含めてひとかたまり。`“ ”` でもよい
  - `-語`：その語を含まないもの
  - `OR`（大文字）：その左右のどちらかに合うもの。`東京 雨 OR 大阪 晴れ` は「東京と雨」か「大阪と晴れ」
  - 大文字と小文字は区別しない
- **日本語**：単語の間に空白の無い文の途中も見つかる（SQLite FTS5 の trigram）。3 文字に満たない語（「雨」「東京」）は trigram の索引では引けないので、索引に入れた文字を順に見て探す。結果は同じで、少し遅いだけ
- 検索欄にマウスを載せると、書き方が出る
- ミュート（[MUTE.md](MUTE.md)）の語句は今までどおり空白区切りだけ。`"` `-` `OR` は使えない

## 1 万件での速さと大きさ

`examples/seed.rs`（50 フィード、1 万件）で測った（2026-10-19、release ビルド、Linux）。

| 検索 | 件数 | 時間 |
|---|---|---|
| `記事 12` | 788 | 46 ms |
| `本文`（本文の中の語） | 10,000 | 53 ms |
| `本`（1 文字） | 10,000 | 50 ms |
| `記事 12 OR 記事 345 -フィード` | 788 | 46 ms |

DB は 39.8 MB。そのうち記事の表が 20.5 MB、索引の文字の写しが 13.7 MB、索引が 4.8 MB だった。seed の本文は同じ文の繰り返しなので、実際の記事では索引はもっと大きくなる（trigram の索引は文字の量の数倍になることがある）。古い記事の整理（既定 30 日）で記事と一緒に消えるので、際限なくは増えない。

## 実装

- DB（スキーマ v8）：`articles_fts`（FTS5、`tokenize = 'trigram'`、列は `title`・`summary`・`body`、`rowid` は記事の id）。記事が消えたときはトリガ `articles_fts_delete` で消す
- 入れるのは Rust（`db.rs` の `index_articles`）。HTML を除くのに `feed::plain_text` を使うので、SQL のトリガではなく Rust で入れる
  - `store_articles`：新しい記事と、タイトル・要約・本文が変わった記事
  - `set_full_content`：全文取得の本文が入ったとき
  - 開いたとき（`index_missing`）：索引に無い記事。v8 にした最初の 1 回は全部の記事がこれで入る（seed の 1 万件で 0.6 秒。起動がその分遅れる）。古いアプリで更新したあとの記事もここで入る
- 検索：`search.rs` の `parse`（語・語句・除外・`OR`）。`db.rs` の `filter` で、3 文字以上の語は `MATCH`、それより短い語は索引の文字への `LIKE`。どちらにもフィード名の `LIKE` を足す
- 古いアプリが v8 のファイルを開いた場合、記事を消すときにはトリガで索引も消える。古いアプリが足した記事は、このアプリで次に開いたときに索引に入る
- モック（`src/dev/mockBackend.ts`）も同じ書き方で、本文まで探す
