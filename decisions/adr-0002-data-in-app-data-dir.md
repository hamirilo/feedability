# ADR-0002: 購読と記事を app_data_dir() の SQLite に置く

**状態**：採用
**日付**：2026-10-17

## 状況

Architecture Standard §6 は「ユーザーのデータを大量に持つツールは、フォルダ 1 つで完結させる」とし、Project Context の雛形はデータの置き場を「`app_data_dir()` の JSON」か「ユーザーが選ぶフォルダ 1 つ（SQLite）」の 2 択にしている。

記事は数千〜数万件になり、未読・スター・検索の問い合わせがあるので JSON 1 ファイルでは足りない。一方で、フォルダを選ばせる（stockroom の形）と、初回に「作る / 開く」の画面を挟むことになる。

## 決定

`app_data_dir()/feedability.db` の SQLite 1 ファイルに置く。フォルダは選ばせない。

- WAL で使い、終了時に `wal_checkpoint(TRUNCATE)` で書き戻してから閉じる（Architecture §6 のとおり）
- スキーマは `PRAGMA user_version` で前方互換に足す
- 持ち運びとバックアップは **OPML の書き出し / 読み込み** で行う。記事そのものはフィードから取り直せる

## 理由

- 記事はフィードから取り直せる二次的なデータで、ユーザーが手で作ったものは購読の一覧（OPML で持ち運べる）とスター程度しかない。フォルダごと持ち運ぶ価値が stockroom ほど大きくない。
- 同期フォルダに置いて複数の PC から開くと、両方が同じフィードを取りに行き、ロックの扱いも要る。1 台に 1 つで足りる。
- 初回に Welcome（作る / 開く）を挟まず、起動してすぐ購読を始められる。

## 影響

- Project Context の「データの置き場」にこの形を書く。
- README の「データ」にファイルの場所とバックアップの方法（アプリを閉じてから `feedability.db` をコピー、または OPML）を書く。
- スター付きの記事は OPML に含まれない。必要になったら書き出しの形を足す。

## 見直す条件

- 複数の PC で既読やスターを揃えたいという要望が出たとき（同期の仕組みを別に考える）。
- 2 つ目のツールが同じ形を選んだら、Project Context の雛形の選択肢に足す PR を desktop-platform に出す。
